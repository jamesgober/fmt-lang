# fmt-lang v0.2.0 — Formatting From Rules

**The foundation.** v0.2.0 turns the scaffold into a working formatter: describe
how a language's nodes and tokens are laid out as data, compile the rules
against the language once, and format any lossless `syntax-lang` tree of it.
Layout is rendered by `pretty-lang`, so groups break only when they do not fit.
Comments are attached by a documented algorithm and never lost or reordered,
error nodes are written as they are, and formatting is idempotent, all backed
by property tests over two languages forged with `lang-forge`.

## What is fmt-lang?

The formatter of the `-lang` family's tooling tier, and the formatter stage of
LexerSketch: a language's formatter is configuration (the sketch's
`[tooling.format]`), not code. `pretty-lang` is the layout algebra; fmt-lang is
the rule model and the walk over the concrete syntax tree that turns rules into
`pretty-lang` documents. It depends on `syntax-lang` and `pretty-lang` only.

## What's new in 0.2.0

### Rules as data

`Rules` holds file-wide settings (indent step, an indentation budget, a
blank-line cap, the final newline, kinds written verbatim such as `ERROR`),
top-level `TokenRule`s, and `NodeRule`s, all keyed by kind names:

```rust
use fmt_lang::{Indent, NodeRule, Rules, Space, TokenRule, Trailing};

let rules = Rules::new()
    .indent(2)
    .verbatim("ERROR")
    .token(TokenRule::new(":").before(Space::None).after(Space::Single))
    .node(
        NodeRule::new("object")
            .group()
            .indent(Indent::Block)
            .delimiters("{", "}", Space::Line)
            .separator(",", Space::Line, Trailing::Never),
    );
# let _ = rules;
```

- A `NodeRule` makes a node a **group**, **indents** its delimited body
  (`Indent::Block`) or every break inside it (`Indent::Hanging`, with chains
  such as `a + b + c` indented once), asks for spacing **before** and **after**
  the node, names list **delimiters** (with spacing just inside them and for an
  empty body) and a **separator** with a **trailing policy**
  (`Preserve`, `Always`, `Never`), caps **blank lines**, and carries **token
  rules** for its direct child tokens.
- A `TokenRule` sets spacing before and after one token kind, or every token,
  at the top level (a default) or inside a node rule (that context, winning).
- `Space` is `None`, `Single`, `SoftLine`, `Line`, or `Hard`, and forms a join
  lattice: when several rules speak about one gap, the gap gets a space if any
  asks for one and breaks as readily as any allows. A gap no rule speaks about
  keeps the source's whitespace.
- `Rules::conventional()` is a preset of common token spacing; its rules are
  `optional`, so it compiles against any language.

`Rules::compile(|name| lang.kind(name))` resolves the names once into a
`Style<K>`, reporting misspelled kinds and inconsistent list rules as
`RuleError`s.

### Formatting

- `format(tree, source, style, width)` is the Tier-1 call.
- `format_keeping(…, keep)` also takes the regions of lexical errors and leaves
  every gap touching one byte for byte as written. An unterminated string ends
  at the line break, so removing that break would pull the next token into it;
  the formatter cannot see that from the tree, the lexer's diagnostics can.
- `format_doc` returns the `pretty_lang::Doc` for rendering into a buffer or
  writer, or at several widths.
- `can_touch` and `Style::with_touch`: where a rule removes whitespace the
  source had, two tokens are written touching only if that cannot fuse them
  (`- -x` never becomes `--x`).

### Comment attachment

Comments are trailing (no line break before them: they stay on the previous
token's line), leading (they start a line, and keep starting one), or dangling
(the last comments of an indented block, indented with it). They never cross a
token, keep their text, and a comment followed by a line break keeps it, so a
line comment always ends its line. The algorithm is documented on `format`.

### Errors and hostile input

- Error nodes named by `Rules::verbatim` are written exactly as in the source;
  only the whitespace around them is formatted.
- Trailing-separator edits apply only to well-formed lists with no error node,
  no node missing a delimiter, and no kept region inside.
- A tree whose tokens do not describe the source is a `FormatError`, never a
  panic.
- Both passes are iterative and linear; a tree nested 200,000 levels deep
  formats, and `Rules::max_indent` caps indentation so output stays linear in
  the input.

## Tests and verification

- **Properties** (`tests/properties.rs`), over random valid programs, token
  soups, and random strings in a JSON-like and a calc-like language forged with
  lang-forge 1.0.1, and over arbitrary hand-built trees with hostile spans:
  idempotence, significant tokens unchanged (modulo trailing-separator
  policies), every comment exactly once and in order, line comments ending
  their line, no trailing spaces introduced, no panics, determinism, and
  formatting with no rules matching a reference implementation written over the
  lexer's flat token list. 13 properties, 400 cases each by default; soaked at
  400,000 cases each before release.
- The soak found four formatter bugs during development, each now a
  regression test: an inserted separator glued to the element instead of
  spaced like a written one; a lone `\r` ending a token or comment fusing with
  the next line break (that break is now written `\r\n`); separator edits in
  lists whose element had a recovered parse error; and unterminated strings and
  comments changed by adding or removing a line break (now the kept-region
  contract).
- **Behaviour tests** (`tests/format.rs`): 36 exact-output tests covering
  spacing, groups, indentation, blank lines, every comment position, error
  nodes, trailing policies, CRLF and BOM, subtrees, kept regions, the
  indentation budget, and invalid trees.

## Dependency wiring

`syntax-lang` 1 (the input tree) and `pretty-lang` 1.0.1 (the layout algebra)
are wired and re-exported whole. `lang-forge` 1.0.1 is a dev-dependency only:
the formatter works on any syntax-lang tree. `diag-lang` is not wired: kept
regions are plain `Span`s.

## Moved to later releases

- **Range formatting** (LSP `rangeFormatting`) is planned for v0.5.0.
- **A trailing comma only when the list breaks** needs a document that renders
  differently flat and broken; pretty-lang 1.x has none. Recorded for
  pretty-lang 2.0.

## Breaking changes

**None.** v0.1.0 had no public API.

## Verification

Run on Windows x86_64 on Rust stable and on the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green on Windows. The Linux and newest-toolchain gates, `cargo deny`, and
`cargo audit` are run centrally before the tag. Counts, identical with all and
with no default features and on 1.85: 8 unit, 36 behaviour, and 13 property
tests, plus 67 doctests (including every `rust` example in `README.md` and
`docs/API.md`; 16 signature-only blocks are not compiled).

Benchmarks (`cargo bench --bench bench`, release profile, Windows x86_64; the
formatter alone, parsing done beforehand):

| Benchmark | Input | Time | Throughput |
|---|---|---:|---:|
| `format_json/rules` | 7.9k nodes (37 KB) | ~2.5 ms | ~3.1M nodes/s (~14 MB/s) |
| `format_json/rules` | 79k nodes (381 KB) | ~51 ms | ~1.6M nodes/s (~7 MB/s) |
| `format_json/rules` | 792k nodes (4.0 MB) | ~645 ms | ~1.2M nodes/s (~6 MB/s) |
| `format_json/doc_only` | 792k nodes, building the `Doc` without rendering it | ~510 ms | ~1.6M nodes/s |
| `format_json/no_rules` | 792k nodes, empty style (whitespace kept) | ~300 ms | ~2.6M nodes/s |
| `format_deep/nested_100k` | a tree nested 100,000 levels deep | ~155 ms | ~0.64M nodes/s |

These are first numbers, not tuned ones, and they were taken on a machine running other builds, so expect ±20%. Throughput falls as inputs grow. A phase split at 792k nodes (one run, same input) showed roughly 15% flattening, 45% building the `Doc`, 15% rendering it, and 25% dropping it: most of the cost is allocating and freeing pretty-lang's reference-counted document nodes (one per text run, break, group, and join). The `Doc` in pretty-lang 1.x has no arena, so that is the next thing to change for speed.
